# Saathi platform spec: elder channels and tenant isolation

## 1. Goal, scope and marks

Goal: the elder reaches the helper on WhatsApp or on a Telegram bot, a channel failure loses no data, the elder bot can never grant an approval, and a second household can be added without a rewrite because one household's bug, key or erasure cannot expose or break another's data (D-79, D-83). This file holds RQ-105 to RQ-108 (channels) and RQ-109, RQ-110, RQ-111a and RQ-111b (tenancy). The channel states and the channel-down rule are RQ-78 in the requests spec; the terms receipts are POLICY-data PL-32; the per-household audit chain is assurance RQ-56a and RQ-56b; the household column test is safety RQ-38. Marks: PRD section 2. All rows are P unless the state column says otherwise. The phase of each row is in the PRD phase table.

Phase choice, for the PRD phase table. RQ-109, RQ-110 and RQ-111a are Phase 0: the Phase 0 tables (`inbox`, `raw_text`, `alert_events`, `audit_log`, the consent rows) and the sender registration of safety RQ-81 are created and read in Phase 0, and a policy, a config row or a key column added after real rows exist means a data migration. RQ-111b is Phase 1: media storage, the second factor and erasure by key destruction first run in Phase 1.

## 2. Elder channels

| ID | Requirement | Check | Evidence and state |
|---|---|---|---|
| RQ-105 | Elder channel port. The core talks to the elder only through the `ElderChannel` port (TRD ports section 2). There are two implementations: `whatsapp` (primary, D-03) and `telegram_elder` (backup, D-79). Core code holds no phone number or chat id: it holds a `PersonRef`, an opaque id that the implementation resolves, and reads a `capabilities` set per implementation (`voice_in`, `voice_out`, `image_in`, `image_out`, `video_in`, `text`, `proactive_free`, `templates`). A proactive message that a channel may not send raises one generic `ProactiveNotAllowed(reason)`: WhatsApp maps its closed window (requests RQ-77) to it, and Telegram never raises it for a chat that has started the bot. Both implementations write the same inbox row and pass the same radar (safety RQ-79, RQ-16); platform facts are fields of the row, not new states. A voice-call implementation is a reserved name with no body (D-80). | one contract test suite runs against the WhatsApp implementation, the Telegram implementation and a fake: each send method, `fetch_media`, `health` and each listed error; a grep test fails when a module outside the implementations imports a platform client or branches on a platform name; a capability-set test; the fake can fail on demand | N: one implementation exists in code and it names the platform in the core |
| RQ-106 | Elder Telegram bot. The elder's Telegram channel is a separate bot, with its own token, username and webhook secret, from the caregiver approval bot (safety RQ-23). Its updates enter through the edge inbox insert (safety RQ-79), authenticated by the secret-token header compared in constant time, and only from a chat id registered for the elder. The elder bot has no callback handler for approvals and no path that mints a token. Its token is held only by the edge and the worker send path; the caregiver bot token is held only by the approval service. A pause, an approval, a `/profile` write, a `/called` entry or a sign-off arrives only from a registered approver chat of the caregiver bot, so approval authority cannot come from the elder bot. Registration: the primary approver creates a one-time start code in the caregiver bot (24 h expiry, single use, stored as a hash); the elder sends it to the elder bot once; spending it binds that chat id to the elder and writes an audit row. An unknown chat id gets no reply and a counted `rejected_inbound` row (safety RQ-81b). | tests: the text "approved" and a forged callback from the elder bot create nothing; an environment test finds no caregiver token in the edge or worker environment and no elder token in the approval service; start code replay, expiry and wrong-elder tests; an unknown chat id test; a registered approver's chat id used on the elder bot gets no approval | N |
| RQ-107 | Channel choice and switching. Per-elder config (RQ-110) holds `elder_channel_active` (`whatsapp` or `telegram`) and the enabled set. Inbound from any enabled channel with a registered identity is persisted, scanned by the radar and processed at once, whichever channel is active. A reply goes out on the channel of the message it answers. Proactive messages (reminders, outcomes, expiry notices, channel notices) go on the active channel. A registered approver switches with `/channel <name>` in the caregiver bot; a confirmation tap is required; the switch writes a `config_change` row and an audit row, and sends the elder a fixed note on both channels. Nothing is copied or migrated: history, open requests, the clarifying state, reminders, consent records and the profile are keyed by `elder_id`, never by channel, so a switch loses no data and changes no request state. A request in `clarifying` has its open question sent once more on the new channel. A switch to a channel with no registered elder identity is refused with the reason, so both channels are registered at onboarding where the elder can use both. | switch test with one request each in `clarifying` and `awaiting_approval` and a due reminder: same request ids and states before and after, question re-sent once; inbound on the inactive channel is processed; refused-switch test; audit, config_change and two-channel notice rows; a switch by the elder bot is ignored | N |
| RQ-108 | Telegram parity. The Telegram elder channel supports everything the elder can do on WhatsApp. In: voice note, photo, video, text, caption, a forwarded message. Out: text, a Hindi voice clip (fixed and dynamic, D-69), an image card (FACT CHECK, PRD RQ-10) and at most 2 quick-reply choices. Differences are declared in `capabilities` and not hidden: Telegram has no templates and no 24 hour window, WhatsApp keeps requests RQ-77. The acknowledgement within 10 s (requests RQ-74), the fixed clips, the stored-audio emergency reply and the language rule (PRD RQ-01) apply to both. A media file over a platform limit ends `media_lost` with the caregiver notice (safety RQ-79). | parity test: every row of the matrix (voice, photo, video, text, forward, voice clip out, image card out, quick replies) runs through the pipeline with fakes on both implementations and reaches the same request state; the 10 s acknowledgement test runs on both | N. R: Telegram file size limits and voice formats were not read |

## 3. Tenant isolation

| ID | Requirement | Check | Evidence and state |
|---|---|---|---|
| RQ-109 | Row-level security. Every table that carries `household_id` has row-level security enabled and forced, with a policy per command that admits a row only when `household_id` equals `current_setting('app.household_id')`; an unset setting admits no row. `Store.tx(household=...)` takes the household as a required argument for every runtime role, with no default, and sets the setting with `SET LOCAL` as its first statement. Scans across households (the worker lease, timers, the reaper, due alert events and the edge's sender lookup) run only through security-definer functions that return ids and no content; all later work runs inside `tx(household=...)`. Only the migrator owns tables, and no runtime role can disable, bypass or alter a policy. The backup and verify roles are read only and are the only roles with `BYPASSRLS`; neither is reachable from a container that holds a model client. A table with `household_id` and no forced policy fails the schema test. | cross-tenant suite: for every household table and every runtime role, with household A set, select, update and delete on a B row touch zero rows and an insert of a B row is refused; an unset setting returns zero rows; a schema test lists tables with `household_id` and fails on one without a forced policy, and is shown to fail on a planted table; sender lookup returns an id and no content | N. E: `001_init.sql` has no policy; `approvals` and `llm_spend` have no `household_id` (threats T-28) |
| RQ-110 | Per-household config rows. Household values live in rows, not in the environment. Table `household_config` holds versioned rows (`household_id`, `version`, `values` validated by schema, `created_by`, `created_at`) for: caps (per order, per day, monthly soft, over-cap thresholds), category and address allowlists, timers and urgent refresh settings (requests RQ-20), the false-alarm budget (safety RQ-18), sender and approver registration, the helper's display name, reply language and ASR language hint (a default, never a code constant), `elder_channel_active` and the enabled set (platform RQ-107), `approval_mode` and approver `visibility` (product RQ-112, RQ-113), `models_local_only` and the tier roster choice (assurance RQ-50), and the `experimental` flag (product RQ-115). Only a `config_change` row by a human identity writes a new version (assurance RQ-95b); agent roles read only. `PolicyConfig` is loaded per household inside commit step 1, under the household lock (safety RQ-83), and the audit row names the version used. An unset value denies (safety RQ-26). The environment holds deployment secrets and technical constants and no household value (POLICY PL-12). | two households with different caps: a commit for A never reads B's version; a new version applies at the next step 1 and its number is in the audit row; agent-role write-denied test; unset-value deny test; grep test that no household value is read from the environment | N. E: caps, allowlists, roster and sender registration come from `Settings` and the environment at 3d46456 (`app.py:152-156`, `engine.py:28-30`) |
| RQ-111a | Envelope keys, Phase 0 scope. Each household has one key per purpose (`content`, `totp`, `audit`), stored in `household_keys(household_id, purpose, key_id, public_key, wrapped_key, created_at, retired_at)`, the secret part wrapped by a key-encryption key that lives outside the database and is its own secret (the PL-14 key class). `content` is a key pair used as a sealed box: the edge holds only the public half, so it can write `raw_text` and cannot read it; the worker and show-raw hold the private half. `totp` and `audit` are random 32-byte secrets. A `key_id` column sits beside every encrypted blob and every keyed hash. In Phase 0, `raw_text.text` is stored encrypted with the household `content` key, and the audit HMAC of assurance RQ-56a uses the household `audit` key. One module encrypts and decrypts. The audit chain hash (assurance RQ-56b) does not use the HMAC key, so a chain still verifies after the `audit` key is destroyed. | canary test: the stored bytes of a `raw_text` row hold no canary; household A's key cannot decrypt B's row; a schema test finds a `key_id` beside every encrypted column and keyed hash; the key-encryption key and every private or secret key are absent from the database, the edge and every container with a model client | N. E: `raw_text` does not exist; the audit HMAC key is one global secret (POLICY PL-14) |
| RQ-111b | Envelope keys, Phase 1 scope. Raw media files are encrypted at rest to the household `content` key; TOTP secrets are encrypted with the household `totp` key (POLICY PL-27); rotation adds a new `key_id`, retires the old and re-encrypts in a job. Erasure also destroys the household's `content`, `totp` and `audit` keys once the erasure record is written. Erasure by key destruction reaches a backup only when no restore can recover the wrapped key; until a restore test shows that, the erasure record keeps listing backups for up to 30 days (assurance RQ-98). | media and TOTP canary tests; rotation test with reads across both `key_id` values; erasure test: after destruction no content decrypts and the chain still verifies; restore test: a dump restored after destruction cannot decrypt the household's content, or the backup stays on the unreachable list | N |

## 4. Out of scope and order of work

Out of scope: the voice-call or IVR channel (deferred, D-80, SPEC evidence section 5), SMS as a notice path, a web app for the caregiver, group chats, a database per household, operator break-glass access, a household-facing export of its own audit trail, and data residency switches beyond `models_local_only`; the last four return when a second household exists. Order of work: the PRD phase table. The port and the WhatsApp implementation come first, and the Telegram implementation follows the Phase 1 split of services. Inside Phase 0 the policies and the `Store.tx` signature come with migrations 002 to 005, before any table is read by application code.

Skipped or not checked: figures (the tables carry the content); Telegram bot limits, privacy mode and terms were not read; no port, bot, fake, policy, key table or config row exists; Postgres policy behaviour for each role was designed from recalled documentation and not run; the encryption library licence is checked by the licence audit when it is added.
