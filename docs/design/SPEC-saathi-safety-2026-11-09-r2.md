# Saathi safety spec: arrival, emergencies, approval, commit and the phone

## 1. Goal, scope and marks

Goal: no elder message is lost, a human always learns of an emergency, and no payment happens without one valid human approval that the code can prove. This file holds RQ-16 to RQ-18, RQ-21 to RQ-23, RQ-25 to RQ-36, RQ-38, RQ-79 to RQ-83, RQ-87 to RQ-89 and RQ-94. Other files: the PRD (behaviour, phases), requests (states, timers), assurance (data, records), evidence (evals, rule index) and POLICY (sandbox, compromise, credentials). Marks: PRD section 2. All rows are P unless the state column says otherwise.

## 2. Arrival and persistence

| ID | Requirement | Check | Evidence and state |
|---|---|---|---|
| RQ-79 | Persist before ack. The webhook handler verifies the signature (RQ-81), inserts one `inbox` row (`provider_message_id` unique, household id, sender id, kind, payload hash, media reference, state `received`, `received_at`) with `ON CONFLICT DO NOTHING`, commits, and only then returns 200. N |
| RQ-81 | Inbound authentication. (a) The WhatsApp signature (HMAC-SHA256 over the raw body, constant-time compare) is checked before parsing; failure returns 401, writes no inbox row and increments a counter. (b) Sender allowlist: only numbers registered for the household (elder, approvers) are processed. | RQ-18 | Emergency escalation, in the order and cadence below. | RQ-82 | Audio that fails ASR (empty result, engine error, confidence below the floor, no language detected) or whose media is lost is forwarded to the caregiver as the original audio, captioned "could not understand" with time and event id, at normal priority with the requests RQ-20 timers. The elder gets a templated "samajh nahi paya, caregiver ko bhej diya, dobara bol sakte hain". Two such audios from one elder within 10 min start RQ-18 stage a. The count joins G-8. Emergency cadence (RQ-18), times from the persisted flag at t0. Values are P defaults in config.

| Stage | Starts | Channel and content | Repeat | Cap |
|---|---|---|---|---|
| a | t0 | Telegram to primary and backup: a one-line event summary, the original audio attached, buttons Acknowledge and False alarm. The transcript is not in the message; "show raw" reads it (assurance RQ-97). | every 60 s for the first 5 sends, then every 5 min | 20 messages per approver |
| b | t0 + 2 min with no ack | WhatsApp template T-01 (requests RQ-77) from the helper number to each approver's personal WhatsApp: event id and "open Telegram", no elder content | every 2 min | 3 per approver |
| c | t0 + 4 min with no ack | Automated voice call through a telephony API, provider named only in private config. Fixed script: "Saathi emergency alert, check your messages, press 1 to acknowledge". Primary first, backup 60 s later | every 3 min per approver | 3 calls per approver, `voice_calls_per_event` per event (default 6) |

The elder hears the 108 and 112 note at t0 and again at t0 + 10 min while no one has acknowledged. A False alarm tap marks the event. Per approver, the counter holds false-alarm events in the last 7 days for which stage b or c had started. When the counter exceeds `false_alarm_budget_per_approver_week` (default 2, so on the third) it opens a threshold review for the radar classifier. It never removes a keyword and never changes a stage.

The false-alarm counter and cadence test cases are in SPEC evidence section 3 (False-alarm counter cases).

## 7. Out of scope and order of work

Out of scope: the telephony provider choice (private config), UI for alerts, any payment path that needs a PIN or OTP, and automatic reconciliation that places an order. Order of work: the PRD phase table. Inside it, the RQ-80 kill tests run before any real order, and RQ-87 to RQ-89 before the first real ride.

Skipped or not checked: figures (tables carry the sequences); the kill, race and counter tests are designs, not run; the telephony drill and the unknown-sender fixtures do not exist; WhatsApp webhook retry after a 5xx (R, documentation not read); the doc lint (SPEC evidence RQ-101) does not exist.
