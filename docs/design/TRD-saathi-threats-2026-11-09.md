# Saathi TRD threats: what stops each threat and what remains

## 1. Scope

Each row names a threat, the controls that stop it by RQ or PL id and the residual risk. The zones, components and edges are in TRD-saathi-2026-11-09.md; the state transitions in the states part. Every control is P until its check in the checks part runs. Where the Phase 0 code lacks the control, the row says so as E with file and line.

## 2. Threat table

| Id | Threat | What stops it | Residual |
|---|---|---|---|
| T-01 | A forward, transcript or OCR text carries instructions ("approve this", "ignore the rules") | Text enters a model only inside a data block; perception and debunk sessions have no tools; planners get typed slots; approval comes only from an authenticated callback of a registered approver; policy and token checks never read text (RQ-33, 22, 23, 30); injection suite per action class | A model can still write a misleading summary or slot. A human sees the card and code compares fields; wrong card text is measured by G-4 edits |
| T-02 | A phone screen carries instructions (notification, review text, address label, driver name, overlay) | RQ-87 reads values from one dump with macro selectors; RQ-88 hostile-screen suite, including an overlay abort; a vision model never supplies a verified value; app allowlist (RQ-90); E-1 conditions (D-53) | Navigation can be steered to extra taps inside the macro bounds (25 actions, 5 min). A hostile screen can force a handoff |
| T-03 | An MCP tool description, schema or result carries instructions | Data wrapping and a per-adapter tool allowlist; adapters are code-driven and parse typed fields; pinned server version and schema hash block the adapter as `unavailable` on change; fixtures per class (RQ-94, 33) | A hosted server that publishes no version cannot be pinned (R: unknown). A false price in a result is caught only by the ceiling, the tolerance and the caregiver |
| T-04 | A spoofed sender or webhook | HMAC over the raw body, constant-time compare, before parsing; sender allowlist; unknown senders get no reply and a keyed-hash row; rate limit (RQ-81). Gap, E: the allowlist reads settings at `app.py:152-156` and an unknown sender only logs at `:155` | Whoever holds the app secret can forge a webhook; PL-14 rotation. A SIM takeover of the elder number is T-17 |
| T-05 | A forged approval: invented tap, edited callback data, "approved" in a WhatsApp message | Only an authenticated Telegram callback from a registered approver creates an approval; callback data carries a nonce, not authority; token signed with at least 32 bytes and bound to request id, quote hash, approver, action and expiry (RQ-22, 23; PL-14). Gap, E: no expiry or request id in `quote.py:69-94` | A taken-over approver account is T-18 |
| T-06 | A replayed approval or callback | Token `spent_at`, `voided_at` and expiry; step 1 spends with `UPDATE ... WHERE spent_at IS NULL`; a replay writes an audit row `deny` (RQ-22) | None beyond the 300 s or 60 s window, in which the same approver may tap again |
| T-07 | A concurrent double commit: two taps, two approvals that together pass a cap, or a tap after an amendment | First tap decides by compare-and-set (RQ-21); household row lock in step 1 (RQ-83); one idempotency key per commit_intent; at most one external call per token; supersede voids tokens (RQ-39) | A service that ignores idempotency keys, plus a crash after the call, can place an order that only reconciliation finds (T-08) |
| T-08 | A crash in the middle of a commit | Three steps with a persisted intent; crash after step 1 means zero calls; a crash after the call leaves `commit_unknown`, reconciled by `find_order`; nothing retries by itself (RQ-80, 35). Gap, E: `commits` has no intent or unknown state (`001_init.sql:94-103`) | An order can exist while unreconciled until `find_order` answers; the caregiver is alerted at once. An adapter without `find_order` cannot commit (RQ-06) |
| T-09 | A lost inbound message | Insert and commit before the 200; unique `provider_message_id`; lease with 5 attempts then `dead` and a caregiver alert; the radar runs on every persisted message (RQ-79, 81). Gap, E: in-memory dedupe and a background task after the answer (`app.py:36-49`, `:159`) | A message the platform never delivers is unknowable. WhatsApp retry after a 5xx is R, not read. A media URL that expires first ends as `media_lost` with a notice |
| T-10 | An emergency missed because ASR failed | The original audio goes to the caregiver and two failures in 10 min start stage a (RQ-82); the radar also scans captions and text; the classifier adds flags (RQ-16). Gap, E: ASR failure becomes a placeholder and no audio forward (`pipeline.py:78-80`) | A clear emergency that ASR renders as harmless text is missed by keywords; recall is bounded by 3/n only after the suite runs (G-6) |
| T-11 | An emergency missed because the approver's phone is muted | Stage a Telegram, stage b WhatsApp template and stage c voice call, each on a cadence until acknowledgement; a `no_human_reached` record in the ops chat (RQ-18, 95a). Gap, E: one channel, in-memory acknowledgement (`telegram.py:45`, `:83-88`) | A phone that is off or in do-not-disturb mode defeats all three channels. SO-1 expiry silences b and c with an owner alert (A05). Telephony delivery is unmeasured until the drill |
| T-12 | An emergency missed in an outage of WhatsApp, Telegram or the models | Stages a and c do not use WhatsApp; stages b and c start at once when Telegram is down (RQ-78); the keyword radar and the stored clips need no model (D-69); daily probe and token-expiry alerts | If Telegram and the telephony provider are both down, only the ops record and the elder's 108 and 112 clip remain |
| T-13 | Cost runaway from a loop, a retry storm or long prompts | Reservation ledger with a hard cap; an unset cap or a missing price disables paid tiers (RQ-48); effort bounds per request and per elder (RQ-92); rate limit (RQ-81c). Gap, E: in-memory ledger, no reservation, price defaults 0 (`gateway.py:88-107`, `:61-62`) | Reservations are worst case; the model role writes ledger rows, so a bug can mis-settle. The cap protects money, not the owner's time |
| T-14 | PII in traces, caches or logs | Redaction before any hosted call, trace or cache write; a field allowlist for spans; raw text only in `raw_text`; trace-canary and redaction suites (RQ-41, 44, 54, 57, 97). Gap, E: prompts and whole node outputs are traced (`gateway.py:209-212`, `pipeline.py:128-135`) | Redaction is pattern based: a name or street outside a pattern passes. Media is outside it and rests on receipts. Traces live 30 days |
| T-15 | A free-tier leak of personal data | `Sensitivity` defaults to PERSONAL; tier F accepts only a `PublicPayload` from allowlisted modules; the egress allowlist drops other hosts (RQ-40, 102). Gap, E: `personal` is a required keyword and False reaches tier F (`gateway.py:182`, `:170-171`) | An allowlisted module could build a `PublicPayload` from personal text; lint and review (PL-16) |
| T-16 | A stolen or reset helper phone | Heartbeat alert; package-drift check; disable the bridge in mesh admin; sign-out runbook and drill (RQ-34, 90, 91; PL-28); the phone holds no credential and no banking app | App sessions stay valid until signed out; a small wallet balance is exposed |
| T-17 | The elder SIM or WhatsApp number is taken over | Sender allowlist plus a human tap for every action (RQ-23, 81); notice on a pattern change; runbook (RQ-91) | An attacker can send false requests and false alarms as the elder. They cannot commit. Re-registering the number takes time |
| T-18 | A Telegram account takeover | Over-cap orders need the TOTP second factor (PL-27); the other approver pauses and removes the row; bot token revoked; only the primary resumes | An attacker with the account can approve under-cap cash orders to allowlisted addresses until noticed; the per-order and per-day caps bound the loss |
| T-19 | An MCP outage or a revoked token | The adapter reports `unavailable`; handoff `no_access`; credential register with a 14 day expiry alert (RQ-06, 93) | The elder waits for a handoff card; no partial order exists because a commit needs a fresh quote and a tap |
| T-20 | A WhatsApp number ban | Channel state `down` from send failure codes, token expiry and the daily probe; open requests end `blocked`, reason `channel_down`; the caregiver is told to phone; stages a and c do not depend on WhatsApp; Telegram-only fallback if the terms forbid the use (RQ-78; PRD section 7) | The elder loses the channel until a new number is approved; template lead times are N |
| T-21 | Supply-chain or licence drift | Lockfile hashes and digest pins; licence audit over packages, images, fonts and model files (RQ-71, 72; PL-09 to 11); MCP schema pins (RQ-94). Gap, E: `latest` tags, an `ffmpeg` apt install, tag-pinned actions (`docker-compose.yml:107`, `:163`; the ASR Dockerfile `:17`; `ci.yml:11`) | A compromised upstream release that matches a digest is not caught. A wheel that bundles a system library needs the image audit (the sherpa-onnx row in the alternatives spec) |
| T-22 | A stale or forged eval receipt | Receipts carry a 40-hex revision compared with `HEAD`, a date inside `valid_days`, a signer and a dataset hash; gates are shown to fail on a deliberate fault; held-out splits are sealed by hash (RQ-58, 62, 100) | A signer can sign a false manual receipt; pull request review (PL-16) is the control |
| T-23 | Tampering with the audit log | Insert-only role; keyed hashes; chain with one serialized writer and a nightly off-site head, verified by `audit_verify.py` (RQ-56a, 56b) | Phase 0 has no chain, so a superuser can rewrite rows until Phase 1; after that, up to a day of rewrite precedes the next head export; the owner holds the superuser |
| T-24 | A wrong number in dynamic audio (amount, ETA) | Text with the facts accompanies the audio (RQ-01); the spoken text comes from the same typed fields as the text reply; fixed clips hold no number except 108 and 112 | The elder may act on a wrong spoken amount; no automatic check of audio content (N) |
| T-25 | A stored voice clip is replaced or corrupted | sha256 in `voice_clips` checked before every send; a mismatch sends text and alerts the owner; clips are versioned rows | An attacker with disk and database access can change both; a mispronounced but intact clip is caught only by the reader's receipt |
| T-26 | A hostile or mislabelled listing makes an item or price look different | Quote facts parsed by code and bound to the hash; live re-read in step 1; ceiling checks; RQ-87 compare; blind-labelled shadow quotes (G-11) | A real service that mislabels an item passes every check; the card is the last check |
| T-27 | A leaked signing or audit key | Separate keys (PL-14); rotate first; rotation voids open tokens; the audit HMAC key stays outside the database (RQ-56a) | Past audit hashes of low-entropy values stay matchable with a leaked HMAC key |
| T-28 | A read across households | `household_id` on every table; the cross-household test; role grants (RQ-38). Gap, E: `approvals` and `llm_spend` lack it (`001_init.sql:83-92`, `:107-114`) | v1 has one household; the test must pass before a second one exists |
| T-29 | A backup or restore leaks or loses data | Encryption before upload with a key apart from the bucket credential; 30 day rolling; monthly restore test that replays the erasure log (RQ-37, 98) | Backups keep erased data for up to 30 days, listed in the erasure record |
| T-30 | The bridge board is compromised over the mesh | The mesh admits the VPS node only; SSH keys from the VPS only; no secret but the mesh key; scheduled updates; outside port scan (RQ-90); commit taps need the commit grant (P) | An attacker on the board can read screens (address, order) and tap non-commit selectors |
| T-31 | A model refuses or returns malformed output in a loop | A refusal is a result field and is never retried on another tier; one schema retry, then failure; the request ends `blocked` with a summary; effort bounds (RQ-47, 49, 92). Gap, E: `cascade` returns the last unaccepted result (`gateway.py:278-280`) | The elder waits for a caregiver summary; the loop costs bounded tokens |
| T-32 | A silent model change alters behaviour | Routing by grade table; sentinel runs on a roster, prompt or harness change; receipts per roster entry (RQ-46, 50, 64) | A provider that changes a model under one name is caught only by the next sentinel run |

## 3. Out of scope

A malicious operating-system user on the VPS; the owner as an attacker; physical coercion of the elder; platform-side breaches at WhatsApp, Telegram or a commerce service beyond the data listed in POLICY-data section 2.

Skipped or not checked: no control was tested; no attack was tried; the likelihood and the loss of each threat were not rated; WhatsApp webhook retry behaviour and platform erasure rules were not read; the sherpa-onnx and licence facts are in the alternatives spec.
